GUIA OPERACIONAL - DEPLOY E ROLLBACK DO PORTAL
================================================

Este documento explica como publicar uma nova versão do Portal ou restaurar
uma versão anterior usando os scripts instalados no servidor.


1. ARQUIVOS E DIRETÓRIOS
------------------------

Projeto:
  /home/metaro/portal-demo

Script de deploy:
  /home/metaro/deploy.sh

Script de rollback:
  /home/metaro/rollback.sh

Configuração dos scripts:
  /etc/portal-deploy.conf

Backups:
  /home/metaro/backup

Logs:
  /home/metaro/log

Aplicação Java:
  /opt/app/app.jar

Frontend publicado pelo Nginx:
  /var/www/app


2. BRANCH UTILIZADA EM CADA AMBIENTE
------------------------------------

Servidor de testes:
  ENVIRONMENT="test"
  DEPLOY_BRANCH="main"

Servidor de produção:
  ENVIRONMENT="production"
  DEPLOY_BRANCH="prod"

Esses valores ficam no arquivo:
  /etc/portal-deploy.conf

Antes de um deploy, confirme o ambiente e a branch:

  source /etc/portal-deploy.conf
  printf 'Ambiente: %s\nBranch: %s\n' "$ENVIRONMENT" "$DEPLOY_BRANCH"

Nunca altere o servidor de produção para usar a branch main ou dev.


3. PRÉ-REQUISITOS PARA UM DEPLOY
--------------------------------

Antes de executar o deploy:

1. Confirme que a alteração foi testada localmente.
2. Confirme que os testes automatizados estão passando.
3. Confirme que o Pull Request chegou à branch correta:
   - main no servidor de testes;
   - prod no servidor de produção.
4. Avise os usuários sobre uma possível indisponibilidade breve.
5. Verifique os serviços:

     systemctl is-active app.service
     systemctl is-active nginx.service

6. Verifique o commit remoto:

     cd /home/metaro/portal-demo
     git fetch origin
     git log --oneline -1 origin/prod

   No servidor de testes, substitua origin/prod por origin/main.

7. Não execute o deploy se houver alterações locais versionadas no servidor.
   O próprio script também fará essa validação.


4. COMO FAZER UM DEPLOY
-----------------------

Execute:

  /home/metaro/deploy.sh

O script realiza automaticamente:

1. Validação do ambiente e das configurações.
2. Atualização do código a partir da branch configurada.
3. Instalação e build do frontend.
4. Build e execução de todos os testes do backend.
5. Validação do JAR e das migrations do Flyway.
6. Preparação dos novos artefatos.
7. Backup do banco, JAR, frontend e application-prod.properties.
8. Publicação e validação do backend.
9. Publicação e validação do frontend.
10. Validação do Nginx.
11. Remoção dos backups excedentes.

O script mantém os 10 backups mais recentes. A quantidade é configurada por:

  BACKUP_KEEP="10"

em:

  /etc/portal-deploy.conf


5. COMO IDENTIFICAR UM DEPLOY BEM-SUCEDIDO
------------------------------------------

No final, deve aparecer:

  [DEPLOY] Deploy concluído com sucesso

Também devem aparecer:

  active
  active

O script informa:

- commit publicado;
- diretório do backup;
- caminho do log;
- histórico do Flyway.

Faça a validação final:

  curl -sS -L -o /dev/null \
    -w 'Frontend: HTTP %{http_code}\n' \
    http://localhost/

  curl -sS -o /dev/null \
    -w 'Backend: HTTP %{http_code}\n' \
    http://localhost:8080/v3/api-docs

O resultado esperado é HTTP 200 para os dois endereços.

Liste os backups:

  /home/metaro/rollback.sh --list


6. O QUE FAZER SE O DEPLOY FALHAR
---------------------------------

Não execute o deploy repetidamente.

Primeiro, observe a etapa e a mensagem [ERRO].

Se a falha ocorreu durante o build ou os testes:

- nenhum artefato foi publicado;
- o banco não foi alterado;
- normalmente não é necessário rollback;
- corrija o código e faça novamente o fluxo de Pull Request.

Confirme:

  systemctl is-active app.service
  systemctl is-active nginx.service

  curl -sS -o /dev/null \
    -w 'Backend: HTTP %{http_code}\n' \
    http://localhost:8080/v3/api-docs

Se a mensagem informar que os artefatos já foram alterados, avalie o rollback
usando o backup indicado pelo próprio deploy.

Consulte o log completo:

  ls -lt /home/metaro/log

  less /home/metaro/log/deploy-AAAAmmdd-HHMMSS.log

Não desative os testes e não altere o deploy para usar -DskipTests.


7. COMO LISTAR OS BACKUPS DISPONÍVEIS
-------------------------------------

Execute:

  /home/metaro/rollback.sh --list

Exemplo:

  20260729-103436 | 85M | deploy concluído

O primeiro campo é o identificador do backup.


8. ROLLBACK NORMAL - SEM RESTAURAR O BANCO
------------------------------------------

Use quando for necessário restaurar:

- JAR do backend;
- frontend;
- application-prod.properties.

O banco permanece no estado atual.

Execute, substituindo DATA_HORA pelo identificador apresentado em --list:

  /home/metaro/rollback.sh DATA_HORA

Exemplo:

  /home/metaro/rollback.sh 20260729-103436

O script solicitará uma confirmação exata:

  ROLLBACK 20260729-103436

Digite a confirmação somente depois de conferir o backup selecionado.

ATENÇÃO:

Se a versão anterior do JAR não for compatível com migrations já aplicadas,
o backend poderá não iniciar. Nesse caso, será necessário avaliar o rollback
com banco.


9. ROLLBACK COMPLETO - INCLUINDO O BANCO
----------------------------------------

Este modo é destrutivo.

Ele restaura o banco exatamente ao estado do backup. Todos os dados criados ou
alterados depois daquele backup serão perdidos.

Use somente quando:

- uma migration deixou o banco incompatível;
- o rollback normal não é suficiente;
- a perda dos dados posteriores foi avaliada e autorizada.

Execute:

  /home/metaro/rollback.sh DATA_HORA --with-database

Exemplo:

  /home/metaro/rollback.sh 20260729-103436 --with-database

O script solicitará:

  ROLLBACK DATABASE 20260729-103436

Não execute esse comando por tentativa. Confirme o horário do backup e o
impacto sobre os dados antes de continuar.


10. BACKUP DE SEGURANÇA CRIADO PELO ROLLBACK
--------------------------------------------

Antes de restaurar qualquer versão, o rollback cria outro backup completo do
estado atual.

Se o rollback falhar, o log informará o identificador desse backup de
segurança.

Não apague esse backup durante uma investigação.


11. VALIDAÇÃO DEPOIS DE UM ROLLBACK
-----------------------------------

Confirme os serviços:

  systemctl is-active app.service
  systemctl is-active nginx.service

Valide frontend e backend:

  curl -sS -L -o /dev/null \
    -w 'Frontend: HTTP %{http_code}\n' \
    http://localhost/

  curl -sS -o /dev/null \
    -w 'Backend: HTTP %{http_code}\n' \
    http://localhost:8080/v3/api-docs

Confira o Flyway:

  sudo -u postgres psql -d db_portal \
    -c "SELECT version, description, success
        FROM flyway_schema_history
        ORDER BY installed_rank;"

Também faça testes funcionais pela interface, principalmente nas funções
afetadas pela versão restaurada.


12. MIGRATIONS DO FLYWAY
------------------------

As migrations ficam no projeto em:

  backend/src/main/resources/db/migration

Regras:

1. Nunca altere uma migration que já foi executada.
2. Crie uma nova versão para cada alteração de banco.
3. Use versões crescentes, por exemplo:

     V3__create_new_table.sql
     V4__add_column_to_table.sql

4. Teste primeiro localmente e no servidor de testes.
5. Promova o mesmo arquivo até a branch prod.
6. O deploy executará automaticamente somente as migrations pendentes.
7. FLYWAY_BASELINE_ON_MIGRATE deve permanecer false.
8. spring.jpa.hibernate.ddl-auto deve permanecer none em produção.


13. COMANDOS QUE NÃO DEVEM SER EXECUTADOS
-----------------------------------------

Não execute sem uma análise e autorização específica:

  rm -rf /home/metaro/backup
  rm -rf /var/www/app
  git reset --hard
  mvn package -DskipTests

Também não:

- apague manualmente o backup mais recente durante uma falha;
- ative novamente FLYWAY_BASELINE_ON_MIGRATE;
- altere migrations já registradas no Flyway;
- execute deploy e rollback ao mesmo tempo;
- copie credenciais ou o application-prod.properties para locais públicos;
- conceda permissão 777 às pastas de backup e log.


14. PERMISSÕES E INFORMAÇÕES SIGILOSAS
--------------------------------------

Os backups contêm:

- cópia completa do banco PostgreSQL;
- application-prod.properties;
- JAR;
- frontend.

O application-prod.properties e o banco podem conter credenciais e informações
sigilosas. O acesso a /home/metaro/backup deve ser restrito a pessoas
autorizadas.


15. RESUMO RÁPIDO
-----------------

Deploy:

  /home/metaro/deploy.sh

Listar backups:

  /home/metaro/rollback.sh --list

Rollback sem banco:

  /home/metaro/rollback.sh DATA_HORA

Rollback com banco:

  /home/metaro/rollback.sh DATA_HORA --with-database

Logs:

  /home/metaro/log

Configuração:

  /etc/portal-deploy.conf

Em caso de dúvida, preserve os serviços e os backups, não repita comandos
destrutivos e procure uma pessoa responsável pela infraestrutura ou pelo
banco de dados.
